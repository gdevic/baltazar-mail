# The Gmail™ adapter

`gmail/api.js` is the Gmail extension's `api.js`, with the same exports as the Yahoo™ adapter (`yahoo/api.js`), so the shared client in `ext/` never knows which one it talks to. This page is how Gmail's concepts are mapped onto the client's, which endpoints are used, and what that costs.

## Sign-in

OAuth 2.0 implicit grant through `chrome.identity.launchWebAuthFlow` (`gmail/auth.js`), which Edge supports as well as Chrome. The flow goes through the user's own OAuth client, whose Client ID the sign-in page's setup guide keeps in local storage (`gmClientId`), else the one a build carries in the manifest's `oauth2` block; a release carries none, and without either the button opens nothing (`NotSignedIn` with code `setup`) and the page shows the guide. The guide is data in `gmail/setup.js`, which the adapter hands out as `setup` (`view`, `check`, `paste`, `at`, `reset`, `explain`) and the shared `ext/guide.js` draws; where it stands is kept in local storage (`gmSetup`) until a sign-in succeeds. The access token lasts an hour and is kept in the extension's session storage (`gmToken`), so it survives a reload but not the browser; the address of the account signed in is kept in local storage (`gmAccount`) until Sign out. It is renewed silently with `prompt=none` and that address as `login_hint`, which succeeds while the browser holds a Google™ session. In the token's last ten minutes the renewal runs beside the requests, which go on using the token until the new one has come, so none of them waits for it; a renewal ahead of time that fails says nothing and is tried again a minute later, unless Google refused it. Requests wait for a renewal only when the token has under a minute left, or after a 401. The browser's silent flow has no deadline of its own, so one without an answer after 20 seconds (`TIMEOUTS.renew`) is given up as a renewal that never reached Google. Only Google's refusal of a silent renewal (`login_required` and the like, or a window that needs the user) is `NotSignedIn`; a renewal that never reached Google (the page could not be loaded, a timeout, a profile check the server failed) is an ordinary error carrying the browser's reason, which the client reports like any connection failure and tries again at the next poll or start-up retry. A renewal is checked against the profile's address, and a token for any other account is refused, so the client never shows one mailbox while acting on another. With no account kept, nothing is tried. Only the sign-in button opens Google's window (`signIn()`); `bootstrap()` never does, so a lost session shows the sign-in page and waits. `signOut()` revokes the token at `oauth2.googleapis.com/revoke` (the token in the form body, never in the URL), which also withdraws the permission; when Google does not confirm it, the user stays signed in and is told so. Otherwise the token and the account are forgotten, a renewal already under way is ignored, and the client clears the address book and loads the page afresh. The scope is `https://mail.google.com/`, the only one that allows permanent deletion (Empty Trash and Spam, Delete in Trash). A token without that scope (the permission left unticked on Google's consent page, or withdrawn since) is answered 403 with `insufficientPermissions` among the errors and `ACCESS_TOKEN_SCOPE_INSUFFICIENT` in the details; either one forgets the token and is `NotSignedIn`, so the sign-in page asks again. A sign-in by the button that fails carries a code (`closed`, `unreachable`, `denied`, `refused` with Google's error, `api-off`, `scope`, `unconfirmed`), which the page turns into a sentence and a fix (`setup.explain`). When Google gave a token but the profile answers 403 with `accessNotConfigured` among the errors and `SERVICE_DISABLED` in the details (the Gmail API off in the client's project), or the profile check could not be made, the token is held in memory and the next press confirms it without opening Google's window again. See `google-setup.md` for the guide and what each of Google's errors means.

## Transport

Every call goes to `https://gmail.googleapis.com/gmail/v1/users/me/...` with `Authorization: Bearer`, under the timeouts of `TIMEOUTS`. A read, and a change of a message's labels (which made twice is made once), is given up when no answer has begun within 12 seconds (`TIMEOUTS.first`) and asked once more with the whole deadline, so a request that went down a dead connection (a computer back from sleep, a network that changed) costs seconds and not the minute; one the browser could not make at all (`Failed to fetch`) is asked again while nothing gets through, as soon as the network is back, for up to a minute from when the connection was lost, and past that fails as `Offline`, which the client tells as the connection's doing. A send, a draft save and an attachment's bytes are asked once, and fail as `Offline` at once when they could not be made. Rate limits (429, or 403 with `rateLimitExceeded`) and server errors are retried three times with backoff, honouring `Retry-After`. A Google Cloud™ project gives each user 6,000 quota units a minute by default (its quota page, "Units per minute per user", shows the value; Gmail's documents name 15,000), so the adapter paces every call under a sliding minute: all calls together may use 5,500 units, or the same share of a lower limit once a refusal of Gmail's has named one (`quota_limit_value`), so the same refusal does not come back every minute. Background work (the address-book build, `list(..., { background: true })`) keeps out of the way of the user's calls, since Gmail also refuses a user's requests that come too fast or too many at once: at most 750 units a minute of its own, batches of 10, one request every 4 seconds, and none while one of the user's requests runs or for 2 seconds after one. A refusal for quota names the minute Gmail counted in (`window_start_time`): a refusal of background work holds background work alone until that minute is over, and a refusal of one of the user's calls holds every call; either is then asked once more. Several reads go in one round trip through `POST /batch/gmail/v1` (multipart/mixed, 50 calls a batch, 10 for background work). Gmail may refuse single items of a batch that itself succeeds; those are asked again in a batch of their own, three times with backoff. A row that still fails fails the list (only a 404 means the message is gone), since a row left out would end the paging early; a label whose counts fail keeps the counts it had. `labelIds` is a repeated URL parameter, never a comma-separated one.

What a call of the user's waits for is told to the client, which says it in its status bar with the seconds left or passed: the pace ("keeping under Gmail's request limit"), the minute of a refusal ("Gmail's request limit is reached"), a retry ("Gmail is busy, asking again"), a sign-in renewal a request has to wait for ("renewing the Google sign-in"), and an answer later than 3 seconds ("no answer from Gmail yet", `TIMEOUTS.slow`). Background work waits unseen. This is `activity` in `ext/adapter.js`, which also keeps every request and every wait that ended, the newest 300 (when, how long, how it ended, what it was, with ids replaced by `*`), for the report a click on the time at the right of the status bar copies.

Quota units of what the client does most: `messages.list` 5, `messages.get` 5 (every row of a list is one get, in a batch), `labels.get` 1, `history.list` 2, `messages.modify` 5, `batchModify` 50, `drafts.create` or `send` 10 to 100. A page of 100 rows seen for the first time is about 505 units; seen before, 5 (see the row cache below). A poll of a mailbox in which nothing happened is 3 (`labels.list` and `history.list`); one that sees a change adds 1 for each label the history names and 1 for the profile; the first one, and one every five minutes, counts every shown label, which is 2 + the number of shown labels; the Starred count is 1, `labels.get` of `STARRED` (`starredCount()`), where a search would fetch every starred message.

## Folders are labels

| Client | Gmail |
|---|---|
| Inbox, Drafts, Sent, Spam (type `BULK`), Trash | the system labels `INBOX`, `DRAFT`, `SENT`, `SPAM`, `TRASH` |
| All Mail (type `ARCHIVE`, id `ALL`) | no label: `messages.list` without `labelIds`, which excludes Spam and Trash |
| a user folder, path `Parent/Child` | a user label, whose `name` is already that path |
| a folder's `unread` and `total` | `labels.get` `messagesUnread` and `messagesTotal`, in one batch, for the labels that changed (see below) |
| hidden folder (type `INVISIBLE`) | a user label with `labelListVisibility: labelHide` |
| not shown at all | `STARRED`, `UNREAD`, `IMPORTANT`, `CHAT`, `CATEGORY_*` |

`highestModSeq`, which the client compares to see whether a folder changed since the last poll, is synthesised: each `folders()` call asks `history.list` from the last history id seen, and every label named in a record (`messagesAdded`, `messagesDeleted`, `labelsAdded`, `labelsRemoved`), plus All Mail, gets the newest history id as its stamp; a change in a label's counts stamps it too. Only the labels the history names are counted again, so a `folders()` call for a mailbox in which nothing happened is two requests, `labels.list` and `history.list`, asked together, and no count. Every label is counted the first time, after a history Gmail no longer holds, after a record that does not name its message's labels, and every five minutes, which catches a count that changed with no record of it; a label not counted yet is counted when it first shows, and one whose counts did not come is asked again at the next call. A history Gmail no longer holds (404, after about a week away) stamps every folder once. The new-mail dot uses Inbox's `messagesUnread`, which is exact.

Folder operations: `labels.create` with `labelListVisibility: labelShow`; `labels.patch` for rename and move (the new name is the new path), repeated for every label nested under the old path, since Gmail does not rename those itself; `labels.delete`; Empty Trash or Spam is `messages.list` of the label followed by `batchDelete`, a page of 500 at a time; Mark all read is `messages.list` with `labelIds=[label, UNREAD]` followed by `batchModify`, in the same pages. Either stops after 200 pages, 100,000 messages, and then fails with a message that says how many were done and to do it again for the rest.

## Rows and bodies

A list is `messages.list` (`labelIds`, `q`, `includeSpamTrash` for Spam and Trash) for ids, then one batch of `messages.get?format=full` with a `fields` mask that leaves the part data out, so a row costs the same 5 units as metadata would and still knows its attachments: each file's `partId`, `filename`, `size`, `type`, `subtype` and `disposition`, so a folder's list of attachments (`has:attachment` in its scope) is built from rows alone. A file's bytes need its `attachmentId`, which `partBytes()` reads from the message's payload (`format=full`, `fields=payload`) when the message has not been opened. A message's headers and parts never change (a draft saved again is a new message), so each row is fetched once and kept, up to 5,000; its labels, which do change, come from what the adapter keeps per message, which its own changes and every record of Gmail's history keep current. A refresh, or a folder opened again, then fetches only the messages it has not seen. A history Gmail no longer holds drops the kept rows and labels. Paging: the client asks by offset, Gmail answers with tokens, so the adapter keeps, per query, the token of where its last page ended; any other offset is walked to from the start with id-only list calls. A request for more than Gmail's 500 ids a page (a refresh of many loaded rows) follows the tokens until it has them all. A row's `folder` is the listed label, or, for a search result and for a row listed in All Mail (which lists every message), Trash, Spam, Drafts, Inbox, the first user label, Sent, or All Mail, in that order; so Archive in the All Mail view takes a message out of Inbox. Address headers are parsed by `rfc822.js` (`parseAddresses`): display names with quotes, comments, groups and RFC 2047 words. An entry that is not one address (several inside one pair of angle brackets, say) is left out, so a name never stands for recipients the reader does not see.

A message's conversation is its thread (`conversation()`): `threads.get` with `format=minimal` and `fields=messages(id,labelIds)` (10 units) names its messages and their labels, those in Spam or Trash are left out, and the rest come as a list's rows do, through the row cache, each in the folder its labels place it in. The client arranges them by the Message-ID, In-Reply-To and References each row carries (`refsOf()`, `ext/thread.js`).

`body()` is `messages.get?format=full` with the data. The text is read from the MIME tree as a mail reader does: an alternative gives its HTML branch (its plain-text branch for `text`), a related part its root, and any other multipart every text part in order, so text after an attachment is shown too; each part is decoded by its charset, and plain text becomes escaped HTML with links. Attachments are the other leaves with a file name or a Content-ID, with Gmail's `partId` and, kept privately, their `attachmentId`. A part is inline only when the HTML shows it as a `cid:` source; Content-Disposition does not decide it, since some mailers mark every attachment inline. A row, which has no HTML, counts a Content-ID part inside `multipart/related` as inline. Inline images are `cid:` references to those parts (`isInlineRef(src, body)` says whether a source names one of that message's own): the client asks `inlineSource()` for each, which fetches the part through `messages.attachments.get` and answers a data: URL. Attachment bytes (`partBytes()`) come the same way; a thumbnail is the image itself when it is under 2 MB. Every attachment can be fetched, so the strip lists them all (`isListed`). Gmail has no document converter and no text extraction, so the viewer shows "No preview available for this file" with Download for formats it cannot draw itself.

Remote images: Gmail returns the sender's HTML as it is, style sheets included, so when the reader loads images they load from the senders' hosts. `IMAGE_SRC` is `https:`, and `imageOrigin()`, which gives the address the client judges a tracking picture by (`ext/pixels.js`), gives a picture's address as it is. The client takes out of those style sheets every rule that reads the message (see SECURITY.md).

## Search

Gmail's search takes any boolean query, so the dialect writes the whole parsed search out (`dialect.compile`): words and quoted phrases, `-` for NOT, `OR`, parentheses, `from:`, `to:`, `subject:`, `has:attachment`, `is:starred`, `is:unread`, `is:read`, `after:` and `before:` with the seconds of the user's own midnight (Gmail reads a date written `YYYY/MM/DD` as midnight Pacific time). The client never needs `query.js`'s evaluation. A folder alone is searched with `labelIds`; a folder with its subfolders through the query, as `(label:"Parent" OR label:"Parent/Child")`, names in quotes with spaces as hyphens; "elsewhere" is the search with `-label:` terms for the scope, with the answer filtered once more by `labelIds` in case Gmail read a name differently. Starred is `is:starred`; a person's mail is `(from:a OR to:a OR cc:a)`, the address reduced to the characters addresses are written with, so nothing in it works as a search operator; "unread in a folder" names the label outside the query.

## Actions

Read, unread, star and unstar change the `UNREAD` and `STARRED` labels: up to ten messages one each with `messages.modify` (5 units each, in one batch, each answered on its own), more with `messages.batchModify` (50 units for up to a thousand, all or none). A move takes away `INBOX`, `SPAM` and `TRASH`, and the user label of the folder the message is shown in (the client passes it as `from`), and adds the target's label; a move to All Mail adds nothing, which is Gmail's archive. The message's other user labels stay, as Gmail keeps them, also through Trash and Spam, whose messages no label's list shows. The answer carries `undo()`, which takes back exactly the labels the move added and removed, so the client's undo restores the message as it was rather than moving it to one folder. Permanent deletion is `batchDelete`, or `drafts.delete` for a draft. The labels of a message not yet seen are fetched first with `format=minimal`.

## Drafts and sending

The message is built as RFC 822 by `rfc822.js build()`: the headers, `Message-ID`, `In-Reply-To` and `References` from the original (fetched once with `format=metadata`; `replyHeaders()` carries over message ids only, of a long chain the first and the newest 19, and none longer than 250 characters, so no header of the original makes the reply one Gmail refuses), the body as quoted-printable `text/html` or `text/plain`, inline images in a `multipart/related` with their Content-ID, files in a `multipart/mixed`; an address is written only when it is one address, and a send or save with any other fails with "Not an address"; forwarded attachments are fetched with `partBytes()` and embedded. It goes up as `uploadType=multipart`: a JSON part naming the thread and, for a draft, its id, then the message.

A draft keeps its draft id across saves while Gmail gives it a new message id each time, so the client's `csid` is the draft id: the first save is `drafts.create` and returns `csid: <draft id>`, which the composer adopts; later saves are `drafts.update`. Draft rows and bodies carry the draft id too, from `drafts.list`, so a reopened draft saves into the same draft and Discard deletes it. The answer names no stored parts, so the composer uploads every file again with each save, which keeps the draft whole. A reply joins the original's thread only while the subjects still match (Gmail's rule); otherwise the message starts a thread, and a thread Gmail refuses (400) is tried once without, for a draft and for `messages.send` alike. Send is `drafts.send` when a draft exists, else `messages.send`; Gmail files the copy in Sent and removes the draft. A draft deleted or sent elsewhere (404) is saved as a new draft, or sent with `messages.send`. A Send pressed while the first save is still uploading waits for it and sends the draft it created. Undo-send stays the client's own timer. Gmail has no "answered" flag to set on the original.

Accounts come from `getProfile` and `settings.sendAs.list`: the primary address and the verified aliases, each with its display name, signature and reply-to.

## Limits worth knowing

`LIMITS.messageBytes` is 25 MB of attachments, Gmail's own send limit. `LIMITS.scanMax` is 2,000 rows per folder for the first address-book build, since every row costs quota, read `LIMITS.scanPage` (20) rows a step. The client starts that build no sooner than `LIMITS.scanAfter` (two minutes) after the mailbox was first opened, a time it keeps in local storage (`contactsAfter`), and takes each step only once the user has left the app alone for `LIMITS.scanIdle` (a minute) or the tab is hidden. At the background pace a step takes about 12 seconds, so the first build, of Sent, Inbox and All Mail, takes up to an hour of such time (a row already read from another folder is not fetched again); a build cut short carries on where it stopped. Later builds stop at the newest row already seen. Label names reach the search only in a folder-with-subfolders scope, in quotes; a name with a double quote in it cannot be searched that way.
